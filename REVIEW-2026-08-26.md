# Smart Garden — Review 2026-08-26

## 1. v1 vs v2 — kiến trúc

v2 chưa commit gì (toàn bộ `smart-garden-v2/` là untracked, `config.h` đang dở dang). Có cả `pcb-v2/` (PCB mới) đi kèm.

**Đổi mới đúng hướng:**
- Tách I/O thành lib ngoài `lib/devicelib` (event-driven, RAII, có CHANGELOG/SemVer/API.md) thay cho `lib/DeviceLib` viết dính vào project như v1.
- Feature-detection qua `__has_include` (PCF8574/Firebase/ESPNOW) thay vì hard dependency.
- Fix leak thật: `esp_timer`/`Ticker` không được cleanup, race condition lúc destructor — đã có trong CHANGELOG 1.2.0.
- Tách pin-mapping ra `config.h` riêng, khớp PCB v2.
- Thêm `envfile` (config persist) và `webota` (OTA) làm lib riêng.

**Cần dọn:**
- `GenericOutputBase.h` include thẳng `ENVFile.h` không qua `__has_include` như 3 tính năng optional còn lại — phá vỡ chính pattern decoupling nó đang dùng.
- File chết còn sót: `SLog.h` include `Logger.h` (không tồn tại trong v2/lib), `WateringSchedule.h` phụ thuộc `Scheduler` đang tắt — cả hai đang sống sót chỉ vì bị comment trong `main.cpp`.
- `devicelib/test/` chỉ có README rỗng dù CHANGELOG claim có test suite.
- `webota`/`envfile` đã nằm trong `lib/` nhưng chưa `#include` ở đâu trong `main.cpp`.
- Chưa commit gì — nên commit theo cụm (lib mới / main.cpp rewrite / config.h) để giữ lại lịch sử quyết định.

## 2. Scheduler v1 — đánh giá

`smart-garden/lib/Scheduler/Scheduler.h` — template tốt (tách generic khỏi domain), hỗ trợ 2 backend (flash file / Firebase RTDB).

Vấn đề:
- `updateTask()` (dòng ~322) lặp `for (auto t: tasks)` — copy theo value, sửa `t` không đụng gì vào `tasks` gốc. Luôn return `true` nhưng không update thật. Chưa gây hại vì hiện không có route `/update-schedule` gọi tới, nhưng là bom hẹn giờ nếu sau này thêm tính năng sửa lịch. Fix: `for (auto &t: tasks)`.
- Serialize/parse thủ công bằng `indexOf("|")`/`substring` thay vì ArduinoJson — lỗi format bị nuốt âm thầm (`Serial.println` rồi bỏ qua), không có log lên Telegram/UI.
- Khớp giờ theo đúng phút hiện tại (`hour==h && minute==m`) — nếu `scheduler.run()` bị block đúng lúc qua phút đó (OTA, chờ Firebase...) thì lịch hôm đó bị bỏ hoàn toàn, không có cơ chế bù giờ.
- **Schedule không thực sự offline-safe**: ở chế độ `STORE_SCHEDULES_IN_DATABASE`, danh sách `tasks` chỉ được nạp trong `FirebaseIOT.onFirstConnected()`. Nếu ESP32 reboot lúc mất mạng, `tasks` rỗng — không tưới gì cho tới khi kết nối lại Firebase.

## 3. Bug thật: lịch tưới chỉ chạy đúng 60s thay vì thời lượng cấu hình

**Nguyên nhân gốc — vòng lặp tự-echo qua Firebase RTDB stream:**

1. `WateringTaskExec()` gọi đúng `Valve.openOnce(duration*60000L, true)` (main.cpp:338) — set custom duration đúng.
2. `Valve.attachDatabase(RTDBObj, "/valve", ...)` (main.cpp:669) → mỗi lần đổi state, `Valve` tự ghi `/data/valve` lên Firebase.
3. Thiết bị đang subscribe realtime toàn bộ `/data` (`setStream`, main.cpp:704) — nhận lại chính write ở bước 2.
4. Nhánh xử lý granular update gọi thẳng, không guard (main.cpp:729-730):
   ```cpp
   } else if (RTDB.dataPath() == "/valve") {
       Valve.setState(RTDB.to<bool>());   // không so sánh state cũ/mới
   }
   ```
   (nhánh `"/"` bên cạnh dùng `syncState()` — có guard `if (state == _state) return;`, nhánh này thì không.)
5. `setState()` → `on(false)` → `VirtualOutput::on()` (VirtualOutput.cpp:7) xoá `_onceTimeDuration = 0` và reset `_previousMillis = millis()` **trước khi** early-return vì valve đã mở sẵn.
6. Từ đó `GenericOutput::loop()` rơi về nhánh default (`_duration = 60000L` set cứng lúc khởi tạo Valve, main.cpp:83), đếm từ mốc thời gian mới → van đóng sau ~60s kể từ lúc Firebase echo về, bất kể cấu hình.
7. "Thỉnh thoảng chạy đúng config" = những lần mạng/Firebase chập chờn nên echo đến muộn hoặc không đến.

**Fix (chưa áp dụng, đang chờ xác nhận từ user):** đổi `Valve.setState(...)` → `Valve.syncState(...)` tại main.cpp:730 (tái dùng guard đã có sẵn, không cần sửa gì trong lib device).

## 4. Firebase RTDB (hoàn thiện auth) vs AWS IoT Core + DynamoDB

| | Production (thiết bị hiện tại) | Giá trị sự nghiệp |
|---|---|---|
| Firebase RTDB + hoàn thiện auth | Rủi ro thấp, đã đi ~90% đường (custom claims + security rules theo uid) | Kỹ năng ít chuyển được sang hệ khác |
| AWS IoT Core + DynamoDB | Chi phí/độ phức tạp vận hành thật (IAM policy, cert rotation, tính phí theo connection/message) | MQTT, Device Shadow, IAM cert-based auth, DynamoDB single-table design — đều là kỹ năng chuẩn ngành, xuất hiện trong JD/interview thật |

**Lưu ý quan trọng:** bug ở mục 3 không phải lỗi kiến trúc của Firebase — là thiếu guard chống tự-echo, có thể tái diễn ở bất kỳ hệ pub/sub nào (kể cả MQTT) nếu không cẩn thận tương tự.

**Khuyến nghị:** hoàn thiện auth trên Firebase cho hệ thống đang chạy thật (ít rủi ro, gần xong). Song song dựng một thiết bị/nhánh riêng để học AWS IoT Core (MQTT + Device Shadow + DynamoDB) như một track học có chủ đích, tách khỏi áp lực uptime của hệ tưới cây đang dùng.

## 5. Định hướng v2: offline-first + tích hợp AWS dần

Mục tiêu của user: thiết bị hoạt động độc lập khi mất mạng, tích hợp AWS IoT Core từng bước.

AWS IoT Core Device Shadow (desired/reported + version, reconcile qua `delta` topic khi reconnect) khớp đúng bài toán này hơn Firebase RTDB stream (yêu cầu kết nối realtime liên tục).

**Nguyên tắc kiến trúc cần áp dụng ở v2** (tách domain logic khỏi sync adapter):
- Nguồn sự thật cho lịch tưới phải là **local** (flash, qua `envfile` đã có sẵn trong v2) — nạp ngay lúc boot, không phụ thuộc network.
- `Scheduler.run()` mỗi tick chỉ đọc local store — không bao giờ gọi cloud để quyết định có tưới hay không.
- MQTT/AWS client là adapter cộng thêm: publish state khi có mạng, nhận `delta` rồi *ghi vào* local store (không thay thế local store). Mất mạng → adapter im lặng, logic tưới vẫn chạy.

**Thứ tự đề xuất:** hoàn thiện local scheduler (flash-based, không phụ thuộc cloud) → thêm MQTT publish state → thêm shadow delta subscribe để nhận lịch mới từ app. Mỗi bước test độc lập được, không bao giờ rơi vào trạng thái "chỉ chạy được khi có cloud".
